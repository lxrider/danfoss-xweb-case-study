# Corrections

Pour proposer une correction non sensible, ouvrir une issue ou une pull request avec :

1. La version du manuscrit et le passage concerné.
2. La correction proposée et son effet sur le raisonnement.
3. Une source publique précise, avec produit, version et section si nécessaire.
4. Les limites de cette source et les explications concurrentes utiles.

Les retours sur les permissions, les journaux, les protections et la récupération sont prioritaires. Une observation issue d'un environnement autorisé peut être décrite sous une forme générale, sans détail d'installation.

Les adresses, comptes, photographies, journaux bruts, noms de clients et données de questionnaires doivent rester hors des issues et des pièces jointes, y compris pendant la revue privée. Les détails d'une vulnérabilité inédite ou les informations permettant de cibler une installation tierce doivent également rester hors des issues publiques. Pour un incident ou une vulnérabilité, utiliser les canaux officiels du fabricant ou du CERT compétent.

Le mainteneur examine l'effet de chaque correction sur les conclusions et leur statut probatoire. Une correction acceptée est intégrée par un commit daté ; son motif est consigné ci-dessous. L'historique conserve les formulations remplacées uniquement lorsqu'elles sont assainies. Toute suppression de données sensibles exige également de traiter l'historique Git.
